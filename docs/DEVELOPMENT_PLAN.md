# 斯诺克 3D 游戏开发方案

## 0. 文档信息

- 文档用途：定义项目的技术路线、开发顺序、系统边界、验收标准和主要风险。
- 当前假设：首个可玩版本面向 PC，优先支持键鼠，手柄作为第二输入方案；先做单机离线，不把联机作为 MVP 的前置条件。
- 核心目标：让玩家感到自己是在真实球桌前观察、入位、瞄准和出杆，而不是在 UI 中选择一个球的结果。
- 技术主线：Unreal Engine 5.x + 独立纯 C++ 物理/规则核心 + UE5 C++ Plugin 适配层 + Blueprint/Actor/DataAsset 内容编排 + 真实 3D 角色与摄像机。
- 重要原则：所有影响球局结果的逻辑必须可记录、可回放、可自动回归测试。

## 1. 产品定位与范围

### 1.1 第一阶段必须实现的体验

玩家能够完成一杆完整的斯诺克击球循环：

1. 在球桌周围移动和观察。
2. 站立、蹲下或低位观察母球、目标球、库边和袋口。
3. 选择“入位”，角色自动进入合理击球姿势，同时允许玩家微调。
4. 在真实 3D 场景中调整球杆方向。
5. 调整母球击打点。
6. 通过拉杆和出杆完成击球。
7. 等待球完全停止，查看进球、犯规和得分结果。
8. 在需要时复盘这一杆的轨迹和碰撞事件。

### 1.2 MVP 不包含的内容

以下功能不应阻塞物理核心和第一条完整击球闭环：

- 在线联机和跨平台同步。
- 复杂的职业生涯、商城和装备养成。
- 多个完整俱乐部场景。
- 高级面部表情和完整观众系统。
- 大量随机球桌状态。
- 复杂的 AI 战术搜索。

这些功能可以在物理、规则和交互稳定后加入。

### 1.3 真实性的定义

本项目的“真实性”分成四层，而不是只看画面：

1. **几何真实性**：球桌、球、库边、袋口和球杆的尺寸与比例可追溯。
2. **动力学真实性**：母球的滑动、滚动、旋转、碰撞、吃库和进袋行为稳定且可解释。
3. **操作真实性**：站位、球杆、架杆、试杆、打点和出杆有明确的空间关系。
4. **比赛真实性**：击球顺序、犯规、罚分、Free Ball、Miss、重摆和彩球阶段符合规则配置。

没有实测数据时，不能声称物理“绝对正确”。项目应先建立参数化模型和可复现测试，再用高质量录像、测量数据或实际球桌实验校准参数。

## 2. 技术栈与职责边界

### 2.1 推荐技术栈

| 层 | 技术 | 责任 |
|---|---|---|
| 引擎 | Unreal Engine 5.x | 渲染、资源、角色、动画、输入、UI、音频、场景、打包 |
| 物理/规则核心 | 独立、C++17 兼容的纯 C++ 源码 | 斯诺克物理、规则、回放、测试、数据验证；不依赖 UE5 |
| UE5 适配层 | C++ Plugin/Module | 将核心状态、事件和数据接入 UE5；转换为 UE 类型 |
| 内容编排 | Actor、Component、Blueprint、DataAsset | 关卡组合、镜头、交互表现、非核心事件编排 |
| 输入 | Enhanced Input | 键鼠、手柄、输入映射和上下文切换 |
| 动画 | Animation Blueprint、Control Rig、IK Rig、IK Retargeter、Sequencer | 入位、手臂、脊椎、骨盆、脚部和球杆约束 |
| UI | UMG；需要统一设计系统时使用 Common UI | 菜单、辅助线、打点控件、比赛信息、回放控件 |
| 版本控制 | Git LFS 或 Perforce | 大型二进制资源、代码和数据资产版本管理 |
| 自动化 | CTest/自定义 C++ 测试 + Unreal Automation Tests | 单元、回归、性能和确定性测试 |
| 分析 | Unreal Insights、CSV/JSON 事件日志 | CPU、物理步耗时、碰撞事件和回放诊断 |
| 独立构建 | CMake + Visual Studio/MSVC | 未安装 UE5 时编译物理核心、规则核心和测试工具 |

### 2.2 引擎物理和自研物理的边界

不要让 Unreal Chaos 直接决定球局结果。建议边界如下：

- **自研 SnookerPhysicsCore**：球、布面、库边、袋口、球杆冲量、旋转、球局快照。
- **Chaos**：角色碰撞、场景道具、非关键装饰物和开发期辅助可视化。
- **UE5 Actor/Component**：把自研物理状态呈现为球、球杆和相关可交互对象。

这样可以避免通用刚体求解器在低速接触、球堆、贴库球和袋口边缘出现难以复现的差异，同时保留引擎的动画和工具能力。

### 2.3 代码模块建议

```text
PhysicsCore/
  include/Snooker/      纯 C++ 公共接口和数据结构
  src/                  几何、球动力学、碰撞和袋口实现
  tests/                纯 C++ 单元和回归测试
  tools/                命令行测试运行器、JSON/CSV 导出和 2D 可视化
  data/                 物理参数、测试快照和基线结果

RulesCore/
  include/Snooker/      规则接口和比赛状态
  src/                  计分、犯规、回合和 frame 状态机
  tests/                规则测试

UnrealProject/Plugins/SnookerPhysics/Source/
  SnookerPhysicsCore/   直接编译或引用 PhysicsCore/RulesCore
  SnookerPhysicsUE/     UE5 类型转换、Subsystem、组件和编辑器工具

UnrealProject/Source/SnookerGame/
  Player/                玩家状态、移动和入位
  Aiming/                瞄准、打点和辅助线
  Camera/                自由观察、入位、跟球和回放镜头
  Presentation/          音效、特效、UI 和镜头表现
  Match/                 比赛流程和场景编排
```

### 2.4 独立核心与 UE5 适配边界

项目必须分成三个层次：

```text
PhysicsCore / RulesCore
    纯 C++，不包含任何 Unreal 头文件
    ↓
SnookerPhysicsUE Plugin
    将纯 C++ 状态和事件适配为 UE5 可用接口
    ↓
SnookerGame
    角色、摄像机、输入、UI、音效、场景和表现
```

`PhysicsCore` 和 `RulesCore` 中禁止使用：

```cpp
#include "CoreMinimal.h"
#include "GameFramework/Actor.h"
#include "UObject/Object.h"
#include "Components/ActorComponent.h"
```

核心层使用自有 `Vec2d`、`Vec3d`、`Quatd`、`Transformd`、`BallState` 和 `PhysicsSnapshot`。进入 UE5 后，只在适配层转换为 `FVector`、`FQuat`、`FTransform` 等 Unreal 类型。

首期建议直接把同一份纯 C++ 源码编译进 UE5 Plugin，而不是立即依赖预编译静态库。这样可以减少 MSVC、Debug/Development/Shipping、运行时库和模块导出差异。核心稳定后再评估静态库或独立动态库封装。

不要把物理参数、规则判断和 UI 控件硬编码在 Actor、Component 或 Blueprint 中。

## 3. 物理系统设计

### 3.1 单位、精度与坐标

- 内部统一使用 SI 单位：米、千克、秒、弧度。
- 球桌长宽、球径、袋口尺寸、库边高度和球杆尺寸全部来自数据资产。
- 代码中不直接散落尺寸常量；独立核心从 JSON/CSV/纯 C++ 配置读取，UE5 表现层可通过 `UDataAsset` 或编辑器工具生成同一份配置。
- 物理计算使用双精度或在关键几何运算中使用双精度；渲染层转换为 Unreal 的 `FVector`、`FQuat` 和 `FTransform`。
- 世界坐标固定约定：桌面平面为 XY，桌面法线为 Z；整个项目禁止模块之间自行改变坐标含义。
- 每个球至少保存：位置、线速度、角速度、半径、质量、睡眠状态、材质配置和当前接触信息。

### 3.2 时间步进

首版建议采用固定时间步长，不依赖渲染帧率：

1. 初始基线使用 240 Hz 物理步。
2. 对连续碰撞和袋口区域支持局部子步或事件细分。
3. 以 120 Hz、240 Hz、480 Hz 三组结果做稳定性比较。
4. 渲染层对物理状态做插值，不能反过来修改物理时间。
5. 每次击球记录物理参数版本、步长、迭代次数和构建版本。

物理频率不是越高越好。最终频率必须以最差目标平台上的帧耗时、碰撞稳定性和回归误差共同决定。

### 3.3 球面动力学

必须区分以下状态，而不是只用一个摩擦系数：

- 滑动：球面接触点相对布面有速度。
- 纯滚动：球面接触点相对布面速度接近零。
- 后旋和前旋：角速度与线速度方向的关系不同。
- 左右旋：影响球与目标球、库边和布面的切向行为。
- 极低速临界状态：避免球无限抖动或在视觉上“粘住”。
- 睡眠状态：只有在位置、速度和角速度都满足阈值后进入。

需要独立实现和测试：

- 布面对球的滑动摩擦。
- 布面对球的滚动阻力。
- 球面旋转导致的切向摩擦。
- 球从滑动过渡到滚动。
- 球杆击打点偏离球心造成的初始角速度。
- 出杆方向、杆头偏移、球杆俯角和冲量。

### 3.4 球与球碰撞

球与球碰撞应使用专用碰撞解算，不把球完全交给通用刚体组件。

每次碰撞需要记录：

- 碰撞时间和物理步序。
- 两球 ID。
- 接触点、法线和相对速度。
- 碰撞前后线速度和角速度。
- 动能变化和能量损失估计。
- 是否是本杆第一次击中目标球。

需要覆盖中心碰撞、薄碰、低速碰撞、旋转碰撞、球堆连续碰撞、贴球和接近睡眠阈值的碰撞。

### 3.5 库边模型

库边由几何轮廓、材料参数和接触规则共同构成，不使用一条无限平面替代：

- 库边台面接触区。
- 橡胶库边接触面。
- 库边顶部和布面的过渡。
- 球贴库时的低速滑动。
- 接近袋口时库边轮廓的变化。
- 旋转球撞库后的速度与角速度变化。

库边参数必须可独立校准，并允许不同球桌预设。

### 3.6 袋口模型

袋口应优先使用可调参数的真实几何碰撞，而不是进入触发器即消失：

- 袋口开口宽度。
- 袋角和袋口边缘。
- 袋底深度与坡度。
- 目标球撞袋角后弹出。
- 球停在袋口边缘。
- 球在袋内滚动、消失和音效触发。

物理系统输出“球进入袋口”“球落到底部”“球弹出”等事件，规则系统再决定是否计分和如何处理。

### 3.7 物理参数数据化

至少建立以下数据资产：

- `TableDefinition`：球桌尺寸、布面边界、库边、袋口、球位。
- `BallMaterialProfile`：球质量、半径、恢复系数和表面参数。
- `ClothProfile`：滑动、滚动、旋转、湿度/布况预设。
- `CushionProfile`：库边弹性和切向参数。
- `PocketProfile`：袋口和袋底几何、进袋阈值。
- `CueProfile`：球杆长度、质量、杆头、最大出杆速度和偏移范围。
- `PhysicsSolverProfile`：时间步、迭代次数、睡眠阈值和容差。

所有参数变更必须带版本号，并能够在回放中还原。

## 4. 交互设计方案

### 4.1 状态机

```text
FreeWalk
  -> Observe
  -> Approach
  -> Aiming
  -> SpinSelect
  -> PracticeStroke
  -> CommitShot
  -> Simulating
  -> ShotReview
  -> FreeWalk
```

每个状态定义：

- 可接受的输入。
- 角色、球杆和摄像机控制权。
- 可见的辅助信息。
- 可以退出的条件。
- 是否允许修改球局数据。

### 4.2 自由移动和观察

默认玩家身高为 175 cm，但角色系统要把身高作为可配置参数，自动影响眼高、肩高、手臂长度、蹲姿和可达范围。

自由观察应支持：

- 围绕球桌行走。
- 站立、蹲下、低位观察。
- 第一人称和第三人称视角。
- 对准母球、目标球、库边和袋口的观察。
- 不遮挡球桌关键区域的镜头碰撞和自动回退。

### 4.3 入位

入位按钮不是瞬移按钮，而是“生成一个可操作的预备姿势”：

1. 根据目标线、母球位置和当前观察方向生成候选站位。
2. 检查玩家胶囊体、球杆、手臂和桌面是否发生不合理穿透。
3. 角色使用脚部、骨盆、脊椎、肩膀、手臂和手腕 IK 进入姿势。
4. 玩家可以通过微调输入修正站位和球杆方向。
5. 无法自然站位时，提示使用架杆、延长杆或换侧观察。

入位辅助只改变角色姿态和默认方向，不能替玩家选择最终击球线路。

### 4.4 三维瞄准

真实球杆始终是最终击球方向的可视表现。输入建议：

- 鼠标拖动：旋转球杆方向。
- 键盘或手柄肩键：粗调。
- 按住精调键或左扳机：慢速微调。
- 可选的相机锁定：保持球杆、母球和目标球关系稳定。

训练模式可显示预测线路、目标球切线和幽灵球；标准比赛模式默认关闭。

### 4.5 打点

不使用强制全屏 2D 打点页面。采用“真实母球 + 局部球面控制器”：

- 母球仍显示在真实桌面位置。
- 屏幕边缘或母球附近出现可收起的球面控制器。
- 点击或拖动球面选取击打点。
- 控制器选择同步到真实球杆杆头位置。
- 极限打点显示出杆风险、滑杆风险和可达性提示。

默认提供中心、高杆、低杆、左塞、右塞和组合偏杆。高级模式可以允许连续二维打点，但必须受到杆头半径和球面可达区域约束。

### 4.6 力度和出杆

核心方案是“真实拉杆”，保留数字反馈但不使用传统力度条作为唯一输入：

1. 玩家按住击球键。
2. 球杆沿自身轴线向后拉。
3. 拉杆距离表达蓄力幅度。
4. 前送速度和出杆平顺度表达最终冲量。
5. 松开按键进入击球提交。

键鼠：按住左键向后拖动，松开完成击球。

手柄：左扳机控制后拉距离，右扳机或释放动作完成出杆；具体映射在原型测试中比较。

保留一个小型力度/冲量反馈环，用于告诉玩家当前可达到的击球范围，但不把它设计成大面积 UI 滑条。

### 4.7 试杆和击球提交

- 允许 1 至 5 次试杆。
- 试杆过程中可以修改方向、站位和打点。
- 释放出杆后进入不可取消的 `CommitShot` 状态。
- 物理开始后锁定玩家输入，直到球局处于稳定状态。
- 球完全停止后恢复观察或进入规则结果界面。

## 5. 比赛规则系统

规则系统与物理系统分离。

### 5.1 物理系统只输出

- 球的轨迹和最终位置。
- 碰撞顺序和碰撞对象。
- 母球首次碰到的球。
- 哪些球进袋以及进袋顺序。
- 球何时全部停止。
- 物理异常，例如穿透、能量爆炸或超时。

### 5.2 规则系统负责

- 当前球员和回合。
- 当前 Ball On。
- 红球和彩球阶段。
- 进球得分。
- 犯规与最低罚分。
- Free Ball。
- Miss 与重打流程。
- 彩球重置。
- 一杆结束、frame 结束、match 结束。
- 比分、剩余分值和安全球状态。

规则配置必须可测试，不能把规则判断藏在球 Actor、Component 或 UI Blueprint 中。

### 5.3 规则优先级

第一版按以下顺序开发：

1. 红球/彩球基本顺序。
2. 进球计分。
3. 母球进袋。
4. 首次碰球错误。
5. 击球未接触目标球。
6. 同杆多球进袋。
7. 彩球阶段。
8. Free Ball。
9. Miss。
10. 重摆、争议和比赛管理细节。

## 6. 角色、摄像机和表现

### 6.1 角色

角色开发不应阻塞物理原型。第一阶段可以使用简化角色，但必须保留：

- 身高参数。
- 胶囊体和桌边碰撞。
- 脚部 IK。
- 脊椎和骨盆调整。
- 持杆手臂 IK。
- 架桥手和球杆约束。

### 6.2 器材

至少支持：

- 普通球杆。
- 架杆。
- 延长杆。
- 蜘蛛架或高架杆。
- 巧克粉和擦杆表现。

器材不是纯 UI 选项。选择器材后应改变球杆模型、姿势、可达范围和击球限制。

### 6.3 摄像机

至少建立：

- 自由观察镜头。
- 低位观察镜头。
- 入位镜头。
- 瞄准镜头。
- 母球跟随镜头。
- 进袋和碰撞回放镜头。
- 俯视分析镜头。

镜头切换使用连续过渡，避免从 3D 场景突然切成独立的平面操作界面。

### 6.4 视觉和听觉反馈

球面、布面、库边、木框、袋口和球杆要使用可区分的材质和声音。至少按以下事件设计音效：

- 杆头接触母球。
- 母球碰目标球。
- 球碰库。
- 多球连续碰撞。
- 目标球落袋。
- 球在袋内滚动。
- 球在低速布面上滚动和停止。
- 架杆、擦粉和脚步。

## 7. 开发阶段和先后顺序

### 7.0 UE5 未安装时的可开发范围

UE5 未安装时，开发工作不能覆盖角色、场景、输入、UI 和最终画面，但不应阻塞最关键的球局模拟。可以先独立完成：

- `PhysicsCore`：球状态、固定步进、摩擦、旋转、球-球碰撞、库边、袋口和异常保护。
- `RulesCore`：Ball On、计分、犯规、回合、彩球阶段、Free Ball、Miss 和 frame 状态机。
- 回放系统：初始快照、击球输入、参数版本、物理事件和最终结果。
- 自动化测试：CTest 或自定义 C++ 测试运行器。
- 调试工具：命令行测试、JSON/CSV 导出、简单 2D 俯视轨迹可视化。

暂时不能完整验证：

- UE5 Plugin/Module 的编译和接入。
- Actor、Component、Blueprint、DataAsset 和编辑器工具。
- 角色动画、Control Rig、IK、摄像机、UMG 和音效。
- UE5 场景渲染、材质、灯光、性能和最终打包。

建议先使用 Visual Studio/MSVC + CMake 编译纯 C++ 核心。安装 UE5 后，将同一份源代码直接纳入 `SnookerPhysics` Plugin 编译，再开始表现层和适配层开发。不要为了提前使用 UE5 类型而把 `FVector`、`UObject` 或 `AActor` 引入核心层。

### M0：项目基线和验证工具

目标：建立可编译、可测试、可记录的项目骨架。

产物：

- PhysicsCore/RulesCore 的 CMake 工程和 C++ 测试框架。
- UE5 工程、Plugin/Module 目录和 Unreal Build Tool 配置；如果 UE5 尚未安装，这部分可以先建立目录和接口，待安装后编译。
- 版本控制与资源目录规范。
- 物理参数资产格式。
- 无 UI 的物理测试运行器和简单 2D/CSV 可视化。
- 日志、快照和回放数据格式。

退出条件：在不依赖 UE5 的命令行测试入口可以运行一个固定球局并输出可比较的 JSON/CSV 结果；UE5 安装后可以用同一组数据通过 Plugin 编译和接入测试。

### M1：桌面几何和最小物理循环

目标：让一个球在独立核心中按可配置桌面移动、摩擦减速并稳定停止。

产物：

- 桌面、布面边界和球模型。
- 固定步进。
- 球的线速度、角速度和睡眠状态。
- 布面滑动/滚动基础模型。
- 位置和速度可通过 CSV、JSON 或简单 2D 工具可视化；UE5 接入后再增加 3D 调试绘制。

退出条件：不同渲染帧率下，同一初始状态的停止位置在设定容差内一致。

### M2：母球击打和旋转

目标：从击球点、杆头速度和球杆方向产生合理初始状态。

产物：

- 击球快照。
- 中杆、前旋、后旋、左塞、右塞。
- 冲量和杆头偏移模型。
- 击球快照可被独立测试和回放；UE5 接入后再制作真实 3D 球杆的可视化。

退出条件：中心击球、高杆、低杆和偏杆均有独立的自动化测试与可观察轨迹。

### M3：球与球碰撞

目标：稳定处理从中心球到球堆的球碰撞。

产物：

- 专用球-球碰撞解算。
- 碰撞事件记录。
- 贴球和低速碰撞处理。
- 球堆测试场景。

退出条件：没有明显穿透、抖动或速度爆炸；同一输入可重放得到同一事件序列。

### M4：库边、袋口和完整桌面

目标：建立可以进行完整练习击球的桌面。

产物：

- 库边几何和材料参数。
- 袋口、袋角、袋底和落袋事件。
- 球贴库、撞袋角和袋口边缘测试。
- 真实桌面资产与物理几何一一对应。

退出条件：一库、两库、薄碰、袋口擦边和进袋失败案例可回归。

### M5：击球交互闭环

目标：玩家可在 3D 场景中完成一杆球。

产物：

- 自由移动和观察。
- 入位。
- 3D 瞄准。
- 球面打点控制器。
- 拉杆出杆。
- 物理模拟到球停的完整状态机。

退出条件：不使用开发者命令，玩家可以完成 20 次不同力度、方向和打点的击球。

### M6：角色、动画和器材

目标：让击球操作看起来和站位逻辑可信。

产物：

- 175cm 默认角色。
- 站立、蹲下、入位、试杆、出杆动画。
- 手臂、手腕、脊椎和脚部 IK。
- 架杆和延长杆。
- 球杆与球的空间约束。

退出条件：常规击球、贴库球、够不到的球和需要架杆的球都有合理姿态或明确拒绝原因。

### M7：规则、计分和比赛循环

目标：完成单人 frame 级别的比赛流程。

产物：

- 球局初始化和球位。
- Ball On、得分、犯规和回合。
- 红球阶段和彩球阶段。
- 母球进袋、Free Ball、Miss、重摆的可配置实现。
- 比分和结果 UI。

退出条件：规则测试覆盖核心正常路径和核心犯规路径；一局可以开始、进行、结束和重新开始。

### M8：训练模式、回放和诊断

目标：让玩家和开发者都能理解击球结果。

产物：

- 轨迹预测辅助。
- 幽灵球和切点显示。
- 物理事件回放。
- 慢放、逐步播放、俯视和自由相机。
- 物理参数和版本显示。

退出条件：任何测试击球都能从同一快照复现，开发者能定位一次异常的第一处错误事件。

### M9：AI 和内容扩展

目标：在物理和规则已经稳定后增加可玩内容。

产物：

- 基于球局状态的候选球搜索。
- 线路、力度和风险评估。
- 训练 AI 和比赛 AI 难度层级。
- 多个球桌场景和球杆预设。

退出条件：AI 使用与玩家相同的物理和规则接口，不通过直接修改球位置作弊。

### M10：性能、发布和联机预研

目标：为正式版本做工程加固。

产物：

- 目标机器性能报告。
- 长时间稳定性测试。
- 存档、崩溃恢复和版本迁移。
- 回放兼容策略。
- 联机同步方案的原型验证。

退出条件：单机版本达到目标平台稳定性；联机只在物理快照和回放模型已经明确后启动。

## 8. 质量保证策略

### 8.1 三类测试

1. **单元测试**：向量、摩擦、碰撞、袋口几何、规则判断。
2. **场景回归测试**：固定初始状态到最终轨迹和事件序列。
3. **人工体验测试**：观察瞄准、入位、出杆、镜头和声音是否有真实感。

### 8.2 物理测试基线

至少建立以下固定案例：

- 中杆直线球。
- 高杆停止球。
- 低杆回旋球。
- 左右塞。
- 中心碰撞和薄碰。
- 一库、两库和三库。
- 贴库低速移动。
- 球堆连续碰撞。
- 袋口正入、擦袋角、停袋口和弹出。
- 极低速接触和睡眠。

每个案例保存初始快照、参数版本、期望事件序列、误差容限和失败截图/轨迹。

### 8.3 验收容差

项目初期先使用工程容差，后续用实测数据替换：

- 事件顺序必须一致。
- 球是否进袋必须一致。
- 最终停止位置、停止时间和速度残差分别记录。
- 不允许穿透、能量爆炸和无原因的长时间抖动。
- 不同渲染帧率不能改变球局结果。

具体数值不要在没有测量依据时伪装成行业标准，应存放在测试配置中并随校准迭代。

## 9. 性能与稳定性目标

- 目标平台上，正常单杆模拟不能因为球碰撞造成可感知卡顿。
- 物理耗时与渲染帧率解耦。
- 每杆球有最长模拟时间和异常保护，防止极端状态卡死。
- 所有异常都输出可重放快照，而不是只输出一句日志。
- 物理核心不得依赖屏幕分辨率、渲染帧率或 UI 状态。
- 运行时参数修改只允许在训练/开发模式启用，正式比赛锁定参数版本。

## 10. 主要风险和处理策略

| 风险 | 影响 | 处理策略 |
|---|---|---|
| 直接依赖通用刚体物理 | 球堆、低速球和袋口不稳定 | 自研球局核心，通用引擎只做非关键物理 |
| 过早制作高质量角色 | 物理和交互未验证就消耗大量资源 | 先用占位角色完成 M5，再做 M6 |
| 没有实验校准数据 | 只能“感觉像真实” | 建立可调参数、固定测试和实测记录流程 |
| 打点和力度过度 UI 化 | 临场感差 | 真实球杆和拉杆为主，局部球面控件为辅 |
| 物理结果不可回放 | 线上 bug 无法复现 | 每杆保存快照、参数版本和事件序列 |
| 规则写在表现层 | 规则扩展和测试困难 | 规则模块只消费物理事件 |
| 角色姿态不可能实现 | 玩家感到假和穿模 | 入位前做可达性检查，失败时明确切换器材或站位 |
| 过早加入联机 | 同步和确定性拖慢核心开发 | 单机回放、快照和确定性先完成 |

## 11. MVP 完成定义

MVP 不是“有一张球桌和几个球”，而是满足以下条件：

- 玩家能从自由观察进入入位、瞄准、打点、试杆、出杆和结果阶段。
- 核心球物理不依赖渲染帧率。
- 至少覆盖中杆、高杆、低杆、左右塞、球碰球、库边和袋口。
- 物理结果有快照和回放。
- 一局基础斯诺克可以开始、进行、计分和结束。
- 规则和物理有自动化测试。
- 玩家无法通过正常输入让球穿透、重复计分或永久卡死。
- 默认视觉和声音已经足以区分击球、碰球、碰库、落袋和停止。

## 12. 推荐的首个执行周期

第一轮只做以下内容：

1. 使用 CMake 创建纯 C++ `PhysicsCore` 和 `RulesCore` 工程。
2. 建立可配置球桌和球数据。
3. 实现一个球的固定步进、摩擦和睡眠。
4. 实现母球中心击打和初步滚动。
5. 创建命令行测试运行器、JSON/CSV 轨迹导出和简单 2D 可视化。
6. 建立第一组 CTest/C++ 自动化回归测试。
7. 安装 UE5 后创建 `SnookerPhysics` Plugin，并用同一份核心源码完成第一次 UE5 编译。

这一轮完成前，不制作完整菜单、职业模式、联网和高精度角色资产。只有先证明独立物理核心可以测量、复现和修改，再接入 UE5 的球体 Actor 和调试场景，后续视觉投入才不会建立在不可控的球局基础上。
